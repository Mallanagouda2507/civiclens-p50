## 1. Overview
In Phase 1, an initial Software Requirements Specification (SRS v1) was synthesized using an AI planning agent. A comprehensive human engineering review identified critical architectural hallucinations, infeasible dependencies, and un-grounded civic assumptions. 

This document catalogs the differences between SRS v1 and the production-verified SRS v2 (IEEE 830 compliant), explaining the engineering rationale for every modification.

---

## 2. Executive Diff Summary Matrix

| Requirement Area | AI-Generated SRS v1 (Raw) | Manually Corrected SRS v2 (Production) | Engineering Rationale & Risk Mitigation |
|---|---|---|---|
| **Duplicate Detection Architecture** | Specified a heavy Deep Learning Transformer embedding model (BERT / Sentence-Transformers) running in Python microservice. | Dual-stage pipeline in pure Node.js: Stage 1 = Geodesic Haversine spatial filter ($\le 75\text{m}$); Stage 2 = Hybrid TF-IDF Cosine ($\ge 0.60$) + Jaccard token overlap. | **Eliminated Python microservice latency & RAM overhead.** Pure Node.js runs natively in-memory without external GPU or C++ compilation. Stage 1 spatial pruning reduces comparisons from $O(N^2)$ to $O(k)$ where $k \ll N$. |
| **Database & Persistence Tier** | Assumed mandatory high-availability cloud MongoDB Replica Set with GeoJSON 2dsphere indexes. | Dual-mode resilient persistence: Checks `mongoose.connection.readyState`. If connected, executes MongoDB 2dsphere queries; if offline, seamlessly falls back to self-contained In-Memory Data Store. | **Zero-Dependency Evaluation Readiness.** Guarantees that automated CI test suites and offline evaluators can run 100% of features without local `mongod` service daemons. |
| **Geographic Coordinate Validation** | Generic worldwide bounding box `[-90, 90]` latitude and `[-180, 180]` longitude without locality enforcement. | Specific municipal boundary checks (configured default: Bangalore Urban coordinates `12.70`–`13.25` N, `77.40`–`77.85` E) plus reverse geocoding locality fallback. | Prevents foreign or nonsensical geotags from polluting municipal dispatch dashboards while permitting global testing. |
| **Duplicate Ticket Policy** | AI suggested automatically deleting or discarding incoming duplicate complaints to conserve database space. | Non-destructive clustering: Child complaints are linked to the master ticket via `masterComplaintId`, incrementing `duplicateCount` and escalating urgency. | **Ethical Civic Fairness.** Deleting duplicates silences citizen endorsements and obscures defect severity. Linking preserves citizen auditability. |
| **Department Routing Classes** | 12 generic unstructured categories (including vague ones like "Miscellaneous", "General", "Administrative"). | Exactly 6 deterministic municipal operational departments: `ROADS`, `WATER_SUPPLY`, `SANITATION`, `ELECTRICITY`, `HEALTH_SAFETY`, `PARKS`, plus explainable keyword attribution. | Direct alignment with real municipal division org charts; provides explainability (XAI) for why a ticket was routed to a given department. |
| **Role-Based Access Control** | Single generic "User" role with optional boolean `isAdmin`. | Granular three-tier RBAC: `citizen`, `staff` (with assigned `department`), and `admin`, enforced via Express JWT middleware. | Municipal field engineers must only review complaints relevant to their department, while citizens only view public progress. |

## 3. Side-by-Side Requirement Code Diff

### 3.1 Duplicate Detection Specification Diff
```diff
--- SRS v1 (AI-Generated Hallucination)
+++ SRS v2 (Human Refactored & Verified)
@@ -45,8 +45,12 @@
- FR-5.1: The system shall pass every incoming complaint description to a BERT
-         transformer embedding pipeline running in a Python FastAPI microservice.
- FR-5.2: The system shall compute vector cosine distance across all historical complaints
-         in the database (O(N) vector similarity search).
- FR-5.3: If cosine similarity > 0.85, the incoming complaint shall be dropped.
+ FR-5.1: The system shall execute a two-stage hybrid duplicate filter in native Node.js.
+ FR-5.2: Stage 1 (Spatial Filter): Execute Haversine geodesic distance calculation.
+         Candidates with distance > 75 meters are immediately pruned (O(1) filter).
+ FR-5.3: Stage 2 (Textual Filter): For candidates within 75 meters, compute hybrid
+         TF-IDF Cosine Similarity (80%) and Jaccard Token Overlap (20%).
+ FR-5.4: If hybrid score >= 0.60, link complaint as a child ticket to the master complaint,
+         increment master duplicateCount, and preserve both records for auditability.
```
