## 3. Detailed User Stories with Gherkin Acceptance Criteria

### Domain A: Citizen User Stories (US-01 to US-08)

#### US-01: Citizen Self-Registration with Password Hashing
- *User Story:* As a citizen, I want to create an account using my name, email, and password so that I can securely submit and manage civic complaints.
- *INVEST Assessment:* Independent of other users; Valuable for identity verification; Testable via bcrypt and DB assertions.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Successful citizen self-registration
    Given an unauthenticated visitor visits the registration endpoint
    When they submit a valid name, unique email, and password with >= 6 characters
    Then the system hashes the password with bcrypt (minimum 10 salt rounds)
    And creates a user record with role "citizen"
    And returns HTTP 201 Created with a signed JWT token valid for 24 hours.
  ```

#### US-02: Citizen Secure Login and JWT Session Issuance
- *User Story:* As a citizen, I want to authenticate with my registered credentials so that I can access my personalized civic dashboard.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Authenticating with valid credentials
    Given a registered citizen with email "citizen@civiclens.gov" and password "password123"
    When they post credentials to "/api/auth/login"
    Then the system validates the bcrypt password hash
    And returns HTTP 200 OK containing an HS256 JWT bearer token and user profile object.
  ```

#### US-03: Coordinate Capture via Mobile Geolocation / GPS
- *User Story:* As a citizen on a mobile device, I want to use my device GPS so that accurate geographic coordinates are attached to my report automatically.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Geolocation coordinate capture
    Given a citizen on the complaint filing view
    When they activate the "Use My Current Location" button
    Then the browser Geolocation API captures latitude and longitude
    And validates the values within [-90, 90] latitude and [-180, 180] longitude
    And places a marker pin on the Leaflet map preview.
  ```

#### US-04: Coordinate Selection via Leaflet Map Pin-Drop
- *User Story:* As a citizen, I want to click anywhere on an interactive map to position a pin so that I can accurately report issues where GPS is inaccurate or unavailable.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Interactive Leaflet pin-drop
    Given a citizen viewing the interactive map picker
    When they click on the map surface at coordinates [77.6412, 12.9784]
    Then the previous marker moves to the selected coordinate
    And the latitude and longitude input fields update reactively.
  ```

#### US-05: Real-Time Duplicate Warning During Complaint Drafting
- *User Story:* As a citizen, I want to be warned if a similar complaint exists within 75 meters so that I do not file redundant reports.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Real-time duplicate alert banner
    Given an existing complaint at [77.6412, 12.9784] titled "Deep road pothole"
    When a citizen sets coordinates within 75 meters and types "Broken asphalt crater"
    Then the frontend queries "/api/ai/duplicate-check"
    And displays a warning banner: "Similar complaint already reported nearby (73% match)".
  ```

#### US-06: Anonymous Submission Option for Public Civic Hazards
- *User Story:* As a citizen, I want to report public hazards anonymously so that my contact details are not stored when reporting sensitive issues.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Anonymous complaint submission
    Given a citizen selects the "Submit Anonymously" option
    When they submit a complaint payload without auth headers
    Then the record stores citizenId as null or "ANONYMOUS"
    And generates a public tracking ID for status follow-up.
  ```

#### US-07: Public Complaint Status Tracking by Reference ID
- *User Story:* As a citizen, I want to enter my tracking ID so that I can verify the step-by-step progress and resolution notes of my grievance.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Querying complaint status by reference ID
    Given an existing complaint with tracking ID "CL-2026-D55057"
    When an unauthenticated citizen requests "/api/complaints/track/CL-2026-D55057"
    Then the response returns HTTP 200 OK with title, department, status, and auditLog timeline.
  ```

#### US-08: Citizen Endorsement / Upvoting of Existing Complaints
- *User Story:* As a citizen viewing an existing nearby complaint, I want to endorse it so that its municipal urgency is elevated without creating a duplicate record.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Endorsing a nearby complaint
    Given an open complaint with duplicateCount = 1
    When a neighboring citizen clicks "Endorse / Also an Issue"
    Then duplicateCount increments to 2
    And priority updates from "LOW" to "MEDIUM".
  ```

### Domain B: Municipal Staff & Field Crew User Stories (US-09 to US-14)

#### US-09: Role-Gated Staff Login & Department Scoping
- *User Story:* As a municipal staff engineer, I want to log in with my credentials so that I only see complaints assigned to my specialized department.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Staff login and department scoping
    Given a staff user with role "staff" and department "ROADS"
    When they log in and query "/api/complaints"
    Then the system returns complaints where department === "ROADS"
    And forbids updating complaints from other departments.
  ```

#### US-10: Staff Triage Dashboard with Department Filtering
- *User Story:* As a municipal officer, I want an interactive triage dashboard so that I can sort, filter, and inspect pending grievances by ward, priority, and date.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Filtering complaints by status on triage dashboard
    Given 20 active complaints across multiple departments
    When the officer applies filter status = "SUBMITTED"
    Then the table renders only unassigned complaints with submission timestamps.
  ```

#### US-11: Review Clustered Duplicate Complaints & Endorsements
- *User Story:* As a triage officer, I want to view all citizen reports grouped under a master complaint so that I understand total citizen impact before dispatching crews.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Viewing linked duplicate tickets
    Given a master ticket with 3 linked child duplicates
    When the officer opens the cluster detail view
    Then all 4 citizen descriptions, timestamps, and locations are displayed side-by-side.
  ```

#### US-12: Status Transition: `SUBMITTED` to `ASSIGNED`
- *User Story:* As a department supervisor, I want to assign a complaint to a specific field engineer so that work order execution begins.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Assigning complaint to field officer
    Given a complaint in "SUBMITTED" status
    When the supervisor sends PUT "/api/complaints/:id/status" with newStatus = "ASSIGNED"
    Then status updates to "ASSIGNED" and an auditLog entry records the supervisor's ID.
  ```

#### US-13: Field Crew Work Order Logging: `IN_PROGRESS`
- *User Story:* As a field repair crew lead, I want to mark a complaint as `IN_PROGRESS` so that the citizen and supervisor know work is underway.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Marking ticket in progress
    Given an assigned complaint
    When the field crew updates status to "IN_PROGRESS" with remarks "Crews dispatched to site"
    Then status becomes "IN_PROGRESS" and citizen tracking reflects active repair.
  ```

#### US-14: Mandatory Resolution Notes & Proof upon `RESOLVED`
- *User Story:* As a municipal officer, I want to close a complaint with mandatory resolution notes so that complete accountability is documented.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Resolving complaint requires resolution notes
    Given a complaint in "IN_PROGRESS" status
    When staff attempts to set status = "RESOLVED" without remarks
    Then the API rejects the request with HTTP 400 Bad Request
    When staff provides valid resolution remarks
    Then status updates to "RESOLVED" and resolution timestamp is stamped.
  ```

  ```gherkin
    When the analytics engine evaluates active tickets
    Then the ticket receives an "SLA_BREACH" flag and renders with a visual alert on the dashboard.
  ```

- *Gherkin Acceptance Scenario:*

  ```gherkin
    When the supervisor opens the Civic Map

    And clicking a pin opens a popup with tracking ID, title, and address.
  ```

- *Gherkin Acceptance Scenario:*
  ```gherkin

    When an admin requests "GET /api/analytics/summary"
  ```

#### US-19: Municipal Complaint Data Export in CSV Format
- *User Story:* As an administrative auditor, I want to export complaint records to CSV so that external compliance audits can be performed.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Exporting complaints to CSV
    When an admin queries "GET /api/complaints/export?format=csv"
    Then the server streams a valid RFC-4180 CSV file with tracking ID, department, coordinates, and status.
  ```

#### US-20: Citizen Account Anonymization under DPDP Act
- *User Story:* As an admin, I want to anonymize personal data upon citizen request so that the platform complies with the Digital Personal Data Protection Act 2023.
- *Gherkin Acceptance Scenario:*
  ```gherkin
  Scenario: Anonymizing citizen account
    Given a citizen requests account deletion
    When admin triggers user anonymization
    Then citizen name and email are replaced with hash tokens
    While complaint civic location and defect history are preserved for infrastructure analysis.
  ```

- [x] **Criterion 2:** Controller, service, and route separation strictly maintained.
- [x] **Criterion 3:** Passing unit tests for normal, edge, and boundary cases.
- [x] **Criterion 4:** Integration tests via Supertest verifying HTTP responses.
- [x] **Criterion 5:** Backend line coverage $\ge 80\%$ (achieved: **84.25%**).
- [x] **Criterion 6:** Critical flows verified by Selenium WebDriver E2E runner.
- [x] **Criterion 7:** Dual-mode persistence verified (MongoDB + In-Memory fallback).
- [x] **Criterion 8:** Zero hardcoded credentials or API secrets.
- [x] **Criterion 9:** Peer human review completed and documented.
